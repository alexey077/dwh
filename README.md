# Домашнее задание №1

Шутов Алексей (`alexey077`). Работа выполнена индивидуально.

В проекте четыре базы PostgreSQL: CRM, каталог, кассовая система POS и склад WMS. У каждого сервиса своя схема и свои данные. Между базами используются логические ссылки по business key. Все четыре базы входят в кластер из трёх узлов PostgreSQL 18 под управлением Patroni.

Patroni выбирает лидера через кворум из трёх etcd. HAProxy направляет запись на лидера, чтение — на реплики. PgBouncer ограничивает число соединений с PostgreSQL и работает в режиме transaction.

## Запуск и полная проверка

Для полной проверки выполни команды из этого раздела. Остальные команды ниже нужны для отдельных действий: повторить чекер, посмотреть контейнеры или остановить стенд.

Нужны Git, Bash, работающий Docker с Compose v2 и Python 3 с модулем `venv`. В CI используется Python 3.12. На macOS сначала открой Docker Desktop и дождись готовности Docker Engine.

Склонируй ветку сдачи и перейди в папку проекта:

```bash
git clone --branch hw1 --single-branch https://github.com/alexey077/dwh.git
cd dwh
```

Запусти полную проверку одной командой:

```bash
./scripts/verify.sh --full
```

Скрипт сам собирает и поднимает стенд, создаёт четыре базы и структуру таблиц, загружает данные и запускает официальный чекер. Затем он выполняет эксперименты Э1–Э7, восстанавливает кластер и повторяет чекер. Окружение Python `.venv` создаётся автоматически. Дождись завершения скрипта и возвращения приглашения терминала. Первый запуск обычно занимает 12–20 минут; загрузка образов при медленном соединении может занять больше времени.

Во время экспериментов скрипт намеренно останавливает контейнеры и меняет лидера. Сообщения об остановке узлов и HTTP 503 в проверке статуса входят в сценарий. Контейнер `init` завершает работу после создания баз; состояние `Exited (0)` для него штатное.

### Как понять, что проверка завершилась

После Э7 чекер должен пройти ещё раз. Последняя строка проверки:

```text
All 139 official checks passed; automatic score 21/21
```

Эта строка появляется дважды: до экспериментов и после них. Если она появилась только до Э1, полный прогон ещё не завершён. Знаки `?` в таблице баллов обозначают пункты для ручной проверки преподавателем.

Результаты сохраняются в папке проекта:

| Файл | Содержимое |
|---|---|
| `reports/check_report.json` | Отчёт чекера до экспериментов |
| `reports/check_after_failures.json` | Отчёт чекера после восстановления кластера |
| `docs/failover_journal.md` | Измерения и вывод экспериментов Э1–Э7 |

Исходный чекер находится в `hw01/` и не изменён. Скрипт `check.sh` запускает его в контейнере с внутренними адресами Docker.

### Если нужна повторная проверка с пустыми базами

Выполни эти команды из папки проекта. Первая команда удаляет контейнеры и данные этого учебного стенда; вторая создаёт и проверяет всё заново.

```bash
docker compose down -v --remove-orphans
./scripts/verify.sh --full
```

Все копии проекта используют одно имя Compose-проекта и одни порты. Поэтому запуск в новой папке использует прежние тома, пока они не удалены командой выше.

### Если Docker пишет TLS handshake timeout

Если ошибка содержит `auth.docker.io` или `registry-1.docker.io`, проверь соединение с Docker Hub:

```bash
docker pull postgres:18
```

При повторном таймауте попробуй другую сеть или переключи VPN. После успешной загрузки повтори `./scripts/verify.sh --full`. Если скрипт завершился с ошибкой, сначала устрани причину и повтори сценарий.

## Отдельные команды

Для обычного полного прогона используй `./scripts/verify.sh --full`. Команды в таблице выполняются по необходимости.

| Команда | Когда использовать |
|---|---|
| `./scripts/verify.sh` | Поднять стенд, загрузить данные и пройти чекер без экспериментов Э1–Э7 |
| `./scripts/check.sh --verbose` | Повторить чекер на уже поднятом стенде |
| `docker compose ps -a` | Посмотреть состояние контейнеров |
| `docker compose down` | Остановить стенд и сохранить базы |

|---|---|

| Каталог через пул | `postgresql://checker:checker@localhost:6432/catalog_service_db` |
| POS через пул | `postgresql://checker:checker@localhost:6432/pos_service_db` |
| WMS через пул | `postgresql://checker:checker@localhost:6432/wms_service_db` |
| HAProxy, лидер | `postgresql://postgres:postgres@localhost:5000/pos_service_db` |
| HAProxy, реплика | `postgresql://checker:checker@localhost:5001/pos_service_db` |
| PostgreSQL pg1 напрямую | `postgresql://postgres:postgres@localhost:5432/pos_service_db` |
| PostgreSQL pg2 напрямую | `postgresql://postgres:postgres@localhost:5433/pos_service_db` |
| PostgreSQL pg3 напрямую | `postgresql://postgres:postgres@localhost:5434/pos_service_db` |

Для другой базы в прямых и балансируемых подключениях заменяется имя базы. Все четыре подключения каждого назначения приведены в манифесте. Роль приложения — `app/app`; роль негативных тестов — `test_writer/test_writer`. Триггеры защищают данные и для этой роли. Прямое изменение остатков приложению запрещено.

Read-only статус для манифеста: `http://localhost:8011/cluster`; штатный ответ Patroni — `http://localhost:8011/native/cluster`. Поле state берётся из реального /patroni каждого узла, replication_state сохраняется отдельно. Остановка узла, неверная роль или отсутствие streaming у реплики даёт HTTP 503. [Выбор формата](docs/adr/007_cluster_status.md).

Patroni API: `http://localhost:8008/cluster`, `http://localhost:8009/cluster`, `http://localhost:8010/cluster`. Изменение конфигурации API требует `patroni/patroni`. Статистика HAProxy: `http://localhost:7005/`. Порты опубликованы на loopback; пароли предназначены для учебного локального стенда.


## Модель и данные

CRM хранит клиентов, контакты, согласия и карты лояльности. Каталог хранит SKU, действующие вещества, производителей и версии цен. POS хранит аптеки, смены, продажи, возвраты и оплаты. WMS хранит закупки, партии, движения и остатки.

Все сущности имеют постоянные business keys. Изменение ключа запрещено триггером. История цен хранится интервалами; цена выбирается в порядке аптека → регион → сеть. В позицию чека записываются цена, название и рецептурность на момент продажи. Изменение каталога не меняет старые чеки.

Остатки обновляются в той же транзакции, что и движение товара. Отрицательный остаток запрещён. Возврат покупателя связан с продажей; суммарно вернуть больше проданного нельзя. Возврат поставщику, брак и просрочка оформляются исходящим движением с причиной в `wms.writeoff_detail`.

Базовая загрузка содержит 2 400 клиентов, 2 100 карт, 600 SKU, 2 016 версий цен, 36 аптек, 4 РЦ, 3 600 партий, 7 200 строк закупок и 24 000 кассовых документов. Данные покрывают не меньше 12 месяцев, включая опорный месяц. Месяц фиксируется при первой загрузке; для воспроизведения его можно задать через `--reference-month YYYY-MM-01`.

Распределения намеренно неравномерны: выходные имеют вес 2, первые 10% SKU — вес 18, первые шесть аптек — вес 5. Вероятность покупки без карты — 45%, возвраты составляют 3% документов. Примерно 20% продаж оплачиваются несколькими способами.

Принятые упрощения: перемещение одной партии считается отдельным заказом доставки; для перемещения в аптеку принят SLA 12 часов. Локальные копии каталога и партий в POS обновляет генератор. После обезличивания клиента продажи сохраняются, но его персональные поля и история очищаются. Будущий DWH должен обработать событие `crm.privacy_event`.

Для CDC настроены `wal_level=logical` и публикации всех таблиц каждого сервиса. У таблиц есть первичные ключи и технические даты. Сам загрузчик CDC относится к следующему заданию.
