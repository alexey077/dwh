Шутов Алексей (`alexey077`). Работа выполнена индивидуально.

В проекте четыре базы PostgreSQL: CRM, каталог, кассовая система POS и склад WMS. У каждого сервиса своя схема и свои данные. Между базами используются логические ссылки по business key. Все четыре базы входят в кластер из трёх узлов PostgreSQL 18 под управлением Patroni.

Patroni выбирает лидера через кворум из трёх etcd. HAProxy направляет запись на лидера, чтение — на реплики. PgBouncer ограничивает число соединений с PostgreSQL и работает в режиме transaction.

## Как запустить

Нужны Git, Bash и работающий Docker с Compose v2. Команды выполняются из корня проекта.

```bash
git clone --branch hw1 https://github.com/alexey077/dwh.git
cd dwh
docker compose up -d --build
./scripts/wait_ready.sh
./scripts/seed.sh --seed 42
./scripts/check.sh --verbose
```

При запуске автоматически создаются четыре базы, таблицы, ограничения и 14 представлений схемы `contract`. Генератор наполняет их согласованными данными. Чекер проверяет структуру, объёмы, качество данных, инварианты, репликацию, CDC и HA. В конце он сам добавляет порцию документов и сравнивает данные лидера и реплики.

Отчёт сохраняется в `reports/check_report.json`. Исходный чекер находится в `hw01/` и не изменён. `check.sh` запускает его в контейнере и подставляет внутренние адреса Docker.

Повторная загрузка с тем же seed и идентификатором порции не создаёт дублей. Пример дополнительной порции из 500 документов:

```bash
./scripts/seed.sh --seed 777 --receipts 500 --batch-id DELTA-MANUAL
```

Повтор этой команды безопасен. Для новой порции при каждом вызове вместо `--batch-id` используется `--next-batch`.

`docker compose down` останавливает стенд и сохраняет данные. `docker compose down -v` удаляет данные; эта команда нужна только для проверки запуска с пустыми томами. Если уже запущена другая копия этого проекта, сначала остановите её: обе копии используют одинаковые порты и имя Compose-проекта.

## Как повторить эксперименты

Для экспериментов нужен Python 3 с модулем `venv`; в CI используется Python 3.12.

```bash
./scripts/verify.sh --full
```

Команда поднимает стенд, загружает данные, запускает официальный чекер, выполняет Э1–Э7 и повторяет чекер после восстановления кластера. Во время экспериментов контейнеры намеренно останавливаются. Результаты: `reports/check_report.json`, `reports/check_after_failures.json` и `docs/failover_journal.md`. Полный прогон в CI занял около 12 минут.

Без `--full` команда выполняет запуск, загрузку и официальный чекер. Дополнительные тесты схемы, повторной загрузки и конкурентных операций запускаются в GitHub Actions.

Для запуска исходного чекера непосредственно с компьютера:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python hw01/hw01_check.py --submission hw01_submission.yaml --json reports/check_report.json --verbose
```

Для другой базы в прямых и балансируемых подключениях заменяется имя базы. Все четыре подключения каждого назначения приведены в манифесте. Роль приложения — `app/app`; роль негативных тестов — `test_writer/test_writer`. Триггеры защищают данные и для этой роли. Прямое изменение остатков приложению запрещено.

Read-only статус для манифеста: `http://localhost:8011/cluster`; штатный ответ Patroni — `http://localhost:8011/native/cluster`. Поле state берётся из реального /patroni каждого узла, replication_state сохраняется отдельно. Остановка узла, неверная роль или отсутствие streaming у реплики даёт HTTP 503. [Выбор формата](docs/adr/007_cluster_status.md).

Patroni API: `http://localhost:8008/cluster`, `http://localhost:8009/cluster`, `http://localhost:8010/cluster`. Изменение конфигурации API требует `patroni/patroni`. Статистика HAProxy: `http://localhost:7005/`. Порты опубликованы на loopback; пароли предназначены для учебного локального стенда.


## Модель и данные

CRM хранит клиентов, контакты, согласия и карты лояльности. Каталог хранит SKU, действующие вещества, производителей и версии цен. POS хранит аптеки, смены, продажи, возвраты и оплаты. WMS хранит закупки, партии, движения и остатки.

Все сущности имеют постоянные business keys. Изменение ключа запрещено триггером. История цен хранится интервалами; цена выбирается в порядке аптека → регион → сеть. В позицию чека записываются цена, название и рецептурность на момент продажи. Изменение каталога не меняет старые чеки.

Остатки обновляются в той же транзакции, что и движение товара. Отрицательный остаток запрещён. Возврат покупателя связан с продажей; суммарно вернуть больше проданного нельзя. Возврат поставщику, брак и просрочка оформляются исходящим движением с причиной в `wms.writeoff_detail`.

Базовая загрузка содержит 2 400 клиентов, 2 100 карт, 600 SKU, 2 016 версий цен, 36 аптек, 4 РЦ, 3 600 партий, 7 200 строк закупок и 24 000 кассовых документов. Данные покрывают не меньше 12 месяцев, включая опорный месяц. Месяц фиксируется при первой загрузке; для воспроизведения его можно задать через `--reference-month YYYY-MM-01`.

Распределения намеренно неравномерны: выходные имеют вес 2, первые 10% SKU — вес 18, первые шесть аптек — вес 5. Вероятность покупки без карты — 45%, возвраты составляют 3% документов. Примерно 20% продаж оплачиваются несколькими способами.

Принятые упрощения: перемещение одной партии считается отдельным заказом доставки; для перемещения в аптеку принят SLA 12 часов. Локальные копии каталога и партий в POS обновляет генератор. После обезличивания клиента продажи сохраняются, но его персональные поля и история очищаются. Будущий DWH должен обработать событие `crm.privacy_event`.

Для CDC настроены `wal_level=logical` и публикации всех таблиц каждого сервиса. У таблиц есть первичные ключи и технические даты. Сам загрузчик CDC относится к следующему заданию.
