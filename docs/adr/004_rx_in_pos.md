# 4. Проверка рецепта в базе POS

Признак рецептурности принадлежит каталогу, но запрет продажи без рецепта должен сработать в POS. Между этими базами нет FK. При этом нельзя просто довериться полю `is_rx_snapshot`, которое пришло вместе с позицией: клиент может передать неверное значение.

Я отказался от проверки только в Python, потому что её можно обойти обычным INSERT. Запрос в каталог из триггера через удалённое соединение тоже не выбрал: тогда доступность кассовой операции зависела бы от другой базы и её текущего состояния.

В POS хранятся локальные версии SKU, цен и партий. Перед загрузкой новой порции их обновляет генератор. Триггер `pos.prepare_line` находит версию SKU на дату продажи и сверяет с ней название и рецептурность позиции. Поэтому передача `is_rx_snapshot=false` для рецептурной версии не позволит обойти проверку. Роли `app` запрещено изменять локальные справочники.

Для рецептурной продажи требуется запись в `pos.prescription`. База проверяет срок рецепта и, если он именной, совпадение клиента с документом. Пустой `prescription_bk` для рецептурной позиции отклоняется с SQLSTATE `23514`. Проверка срока годности партии выполняется там же по локальной копии WMS.

Цена решения — копии справочников могут отставать. В этом ДЗ их согласованность поддерживает генератор; для самостоятельной кассовой системы понадобился бы постоянный обмен изменениями. Если нужной версии нет в локальной копии, запись позиции отклоняется.

Реализация: [модель POS](../../migrations/pos/001_pos.sql), [синхронизация справочников](../../scripts/seed.py) и [права ролей](../../scripts/migrate.py). Продажу без рецепта проверяет [I10](../../tests/invariants/I10_rx_no_script.sql).
