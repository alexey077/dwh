# 7. Проверка состояния кластера через API

У Patroni 4.1.5 два разных сведения попадают в похожие поля. В `/cluster` у реплики может быть `state=streaming`. В её собственном `/patroni` при этом указаны `state=running` и `replication_state=streaming`: PostgreSQL запущен и принимает WAL. Исходный чекер ожидает именно состояние процесса `running` у всех узлов.

Я не стал менять официальный чекер. Простую замену слова `streaming` на `running` в ответе тоже отверг: запись в составе кластера ещё не доказывает, что конкретный PostgreSQL сейчас доступен и репликация работает.

Для этого добавлен сервис `cluster-status`. На каждый запрос он получает состав кластера и отдельно опрашивает `/patroni` всех трёх узлов. В сводном ответе состояние процесса берётся из `/patroni.state`, а состояние репликации сохраняется отдельно. Также сверяются имена, роли и идентификаторы кластера. Реплика должна действительно сообщать о приёме WAL.

Сводный `/cluster` возвращает HTTP 503, если узел недоступен, PostgreSQL остановлен, роли не совпали или реплика перестала принимать WAL. Исходный ответ Patroni доступен без изменений по `/native/cluster`. Это позволяет проверить, откуда взяты сведения.

Понадобился дополнительный сервис наблюдения, который сам может отказать. Он не участвует в выборе лидера и SQL-соединениях: HAProxy обращается к штатным API Patroni. При отказе сервиса пропадёт сводный статус, но маршрутизация запросов к базам от него не зависит.

Реализация: [сервис статуса](../../scripts/cluster_status.py). [Проверка с остановкой настоящего узла](../../tests/check_cluster_status.py) подтверждает переход сводного статуса в HTTP 503 и восстановление после запуска.
