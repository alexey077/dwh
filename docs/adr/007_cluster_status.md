# 7. Состояние PostgreSQL и состояние репликации

## Задача

Patroni 4.1.5 в /cluster показывает для реплики streaming, а в /patroni той же реплики state=running и replication_state=streaming. Исходный чекер требует state=running у всех членов. Состояние процесса и состояние потока — разные сведения.

## Решение

Выбрал read-only сервис cluster-status на порту 8011. Он получает настоящий /cluster и настоящий /patroni каждого из трёх узлов. Роль берётся из состава кластера и сверяется с ролью живого PostgreSQL. Поле state копируется из /patroni.state; replication_state и полный исходный ответ узла сохраняются отдельно. /native/cluster возвращает штатный ответ Patroni без изменений.

Недоступный узел, остановленный PostgreSQL, отсутствие streaming у реплики, несовпадение имён, system identifier или ролей приводят к HTTP 503. Каждый запрос получает свежие данные. Остановка настоящей реплики проверяется отдельно в CI.

## Почему не другой вариант

Вариант ослабить чекер или игнорировать его HA-ошибку отверг: это не подтверждает выполнение всех проверок. Слепую замену streaming на running отверг: она могла бы скрывать реальный отказ. Устаревшую версию Patroni ради другого формата ответа отверг: в семинаре используется 4.1.5 с PostgreSQL 18.

## Последствия

появился дополнительный сервис наблюдения. Он не управляет выборами лидера и не участвует в маршруте SQL; HAProxy и эксперименты используют штатные API Patroni. При его отказе недоступен только объединённый статус. Все исходные файлы hw01 сохранены, оба полных запуска чекера в CI обязаны пройти без исключений.
